# 진행 서버 저장 설계 (1단계: 진행 안 날아가게)

> 지금 섬마을의 진행(`progressStore`, 키 `fishing-island-save-v1`)은 브라우저 localStorage 에만 있다. 브라우저 데이터를 지우거나 주소가 바뀌면(rinfish → seommaeul 때처럼) 진행이 사라진다. 이 설계는 진행을 Cloudflare 서버(Durable Object 저장소)에 보관한다. 사용자 결정(2026-11-26)을 따른다.

## 목표와 성공 기준

- 진행이 서버에 저장되어, 브라우저 데이터를 지우거나 다른 기기·주소에서 들어와도 **복구 코드**로 되찾을 수 있다.
- 서버나 인터넷이 끊겨도 혼자 하기는 지금처럼 플레이된다. 돌아오면 밀린 저장을 올린다.
- 같은 진행을 두 곳(탭 두 개, 기기 두 대)에서 동시에 해도 저장이 뒤섞이지 않는다. 오래된 쪽이 최신을 받아 이어 한다.
- 기존 유저의 localStorage 진행은 첫 접속 때 자동으로 서버로 올라간다. 아무것도 잃지 않는다.
- 서버 주소(`VITE_ROOM_SERVER`)가 없는 개발 환경에서는 지금과 똑같이 localStorage 만으로 동작한다.

## 정해진 규칙 (사용자 결정)

| 주제 | 결정 |
|---|---|
| 단계 | **1단계: 진행 안 날아가게**(이 문서). **2단계: 조작(치트) 막기**는 나중에 별도 설계 |
| 서버 장애 | **계속 플레이**. 브라우저 사본으로 진행하고, 서버가 돌아오면 올린다 |
| 식별 | 우선 **복구 코드**. **허브 로그인이 구현되면 로그인 방식으로 바꾼다** (아래 "허브 로그인 전환" 참고) |
| 저장 방식 | 방 서버 워커(`rinfish-rooms`)에 저장 주소를 더하고, **복구 코드마다 Durable Object(`Save`) 하나** |
| 충돌 | 저장 번호(`rev`)로 판정. **서버가 더 최신이면 서버 것을 받는다** |

## 무엇을 어디에 두나

| 위치 | 데이터 |
|---|---|
| **서버 (`Save` 객체)** | `progressStore` 저장본 전체: look, coins, gear, ammo, reserve, inventory, items, snacks, bait, selectedBait, feed, dex, rangeBest, playTime, unlockedZones, doors, aquarium, stock, survival, clock (persist `version` 포함) |
| **브라우저만** | 설정(`fishing-island-settings-v1`), 마지막 위치(`fishing-island-place-v1`), 닉네임·마지막 방(`fishing-island-net-v1`), 허브 복귀 주소(sessionStorage), 애셋 캐시 |
| **브라우저 (새로)** | 복구 코드, 서버와 마지막으로 맞춘 저장 번호 (`seommaeul-cloud-v1`) |
| **브라우저 (그대로, 역할만 바뀜)** | `fishing-island-save-v1` 는 **사본**이 된다. 정본은 서버 |

마지막 위치는 이번에 옮기지 않는다. 다른 기기에서는 선착장에서 시작할 뿐이라 손해가 작다.

## 구조

```
브라우저                                     Cloudflare 워커 rinfish-rooms
┌───────────────────────────┐               ┌──────────────────────────────────┐
│ progressStore (zustand)    │               │ /rooms/<id>  → Room  (그대로)      │
│  └ persist → localStorage  │               │ /save        → Save 객체          │
│ cloudSave                  │──HTTPS(JSON)──▶│    이름 = sha256(복구 코드)        │
│  └ 복구 코드·synced rev    │               │    저장소: { rev, data, savedAt }  │
└───────────────────────────┘               └──────────────────────────────────┘
```

### 서버

- `wrangler.toml` 에 `SAVE` 바인딩(`class_name = "Save"`)과 마이그레이션 `v2`(`new_sqlite_classes = ["Save"]`)를 더한다.
- 저장 주소는 `ROOM_SERVER` 에서 만든다: `wss://…` → `https://…`, `ws://…` → `http://…`, 뒤에 `/save`.
- 요청 머리말 `Authorization: Bearer <복구 코드>` 로 코드를 받는다. 주소(URL)에 코드를 넣지 않는다 (로그·기록에 남지 않게).
- 워커는 코드 형식을 검사한 뒤 `sha256(코드)` 를 객체 이름으로 써서 `env.SAVE.idFromName(...)` 로 넘긴다. **코드 원문은 어디에도 저장하지 않는다.**
- `Save` 객체 저장소에는 `save` 키 하나: `{ rev: number, data: unknown, savedAt: number }`.

| 요청 | 동작 | 응답 |
|---|---|---|
| `GET /save` | 저장본 읽기 | `200 {rev, data, savedAt}` / 없으면 `404` |
| `PUT /save` 본문 `{baseRev, data}` | `baseRev` 가 서버 `rev` 와 같으면(없으면 0) 저장하고 `rev+1` | `200 {rev}` |
| | `baseRev` 가 서버 `rev` 와 다르면 저장하지 않음 | `409 {rev, data, savedAt}` (서버 최신본) |
| 그 밖 | 코드 형식 틀림 `401`, 본문 너무 큼 `413`, 본문이 JSON 객체가 아님 `400`, 다른 주소 `404` | |

- 본문 크기 한도 **256KB**. 지금 저장본은 수 KB 라 넉넉하다.
- 서버는 `data` 내용을 검사하지 않는다 (1단계). 불러올 때 클라이언트의 기존 `migrate`·`merge` 가 검증한다.
- CORS: 게임 주소(`https://seommaeul.vercel.app`, 로컬 개발 `http://localhost:*`, `http://127.0.0.1:*`)만 허용한다. `OPTIONS` 미리 요청에 답한다. 허용 목록은 워커 상수로 둔다.
- 오래 안 쓴 저장은 1단계에서 지우지 않는다.

### 복구 코드

- 글자: `23456789ABCDEFGHJKMNPQRSTVWXYZ` (헷갈리는 0·O·1·I·L·U 뺌, 30자). **20자**(약 98비트). 보일 때는 `QX7K-29PM-H4TB-8WNC-5RDA` 처럼 4자씩 끊는다.
- 브라우저 `crypto.getRandomValues` 로 만든다. 입력받을 때는 대문자로 바꾸고 `-`·공백을 지운 뒤 글자·길이를 검사한다. 서버도 같은 검사를 한다.
- 코드는 비밀번호와 같다. 아는 사람은 그 진행을 읽고 덮어쓸 수 있다. 화면 안내에 "남에게 보여 주지 마세요" 를 적는다.

### 클라이언트 (`cloudSave`)

`progressStore` 의 persist 저장소를 감싸는 모듈 하나가 서버와 주고받는다. 게임 로직은 바뀌지 않는다.

- 상태: `code`, `syncedRev`(서버와 마지막으로 맞춘 번호), `dirty`(올리지 못한 변경 있음), `status`(`off` | `syncing` | `saved` | `pending`).
- `code`·`syncedRev` 는 localStorage `seommaeul-cloud-v1` 에 둔다.

**시작할 때 (로딩 화면 동안)**

1. persist 가 localStorage 사본으로 상태를 채운다 (지금과 같음).
2. 코드가 없으면 새로 만든다.
3. `GET /save` (최대 3초 기다림).
   - `404`: 지금 사본을 `PUT {baseRev: 0}` 으로 올린다. **기존 유저의 진행이 이때 서버로 옮겨진다.** 새 유저는 초기 상태가 올라간다.
   - `200` 이고 `rev > syncedRev`: 서버본을 받는다 (아래 "서버본 적용").
   - `200` 이고 `rev == syncedRev`: 사본에 올리지 못한 변경(`dirty`)이 있으면 올리고, 없으면 그대로.
   - 실패·시간 초과: 사본으로 플레이하고 `pending`. 30초마다 다시 시도한다.
4. 로딩 화면은 이 단계를 최대 3초까지만 기다린다. 지금 로딩 화면이 모델을 받는 동안 대부분 끝난다.

**플레이 중**

- persist 가 localStorage 에 쓸 때마다 `dirty = true` 로 표시한다 (기존 `deferrableStorage` 그대로).
- `dirty` 이면 **마지막 변경 후 3초**(최대 15초마다 한 번)에 `PUT {baseRev: syncedRev, data}`. 성공하면 `syncedRev = rev`, `dirty = false`.
- 탭을 숨기거나 닫을 때(`visibilitychange` → hidden, `pagehide`): 미룬 저장을 먼저 쓰고(`flush`), `fetch(..., {keepalive: true})` 로 바로 올린다.
- 실패하면 `pending` 으로 두고 5초 → 15초 → 30초 간격으로 다시 시도한다. 사본은 이미 localStorage 에 있으니 진행은 잃지 않는다.

**충돌 (`409`)**

- 다른 탭·기기가 먼저 저장했다는 뜻이다. 서버본을 받는다(서버본 적용) 그리고 "다른 곳에서 한 진행으로 바꿨어요" 토스트를 띄운다.
- 이 탭에서 올리지 못한 마지막 변경(보통 몇 초)은 사라진다. 단순한 규칙을 위해 받아들인다.

**서버본 적용**

- 서버 `data` 를 localStorage 사본에 쓰고 `useProgressStore.persist.rehydrate()` 로 다시 불러온다. 기존 `migrate`(버전 올리기)·`merge`(값 검증)를 그대로 거친다.
- `syncedRev` 를 서버 `rev` 로 맞추고 `dirty = false`.
- 플레이 도중(낚시 중, 요리 중)에 바뀌면 화면 상태와 어긋날 수 있다. 시작할 때는 로딩 화면 뒤라 문제없고, 플레이 중 충돌은 드물어서 1단계에서는 그대로 바꾼다.

**서버 없음**

- `ROOM_SERVER` 가 없으면 `cloudSave` 는 아무것도 하지 않고(`off`) 복구 코드 화면도 숨긴다. 지금과 똑같다.

| 곳 | 내용 |
|---|---|
| HUD 구석 | `☁️ 저장됨` / `☁️ 저장 중…` / `☁️ 저장 대기 중` (작게). `off` 면 없음 |
| ESC 메뉴 → 「☁️ 진행 저장」 | 내 복구 코드(4자씩), 「복사」 버튼, 안내: "브라우저를 지우거나 다른 기기에서 이어 하려면 이 코드가 필요해요. 남에게 보여 주지 마세요." |
| 같은 창 | 「코드로 이어 하기」 입력칸 (아래) |
| 시작 창(로비) | 「🔑 코드로 이어 하기」 버튼 → 같은 입력칸 |

**코드로 이어 하기**

1. 코드를 입력하면 형식을 검사하고 `GET /save` (그 코드로).
2. `404` → "그 코드로 저장된 진행이 없어요".
3. `200` → 확인 창: "지금 이 브라우저의 진행(코인 N, 도감 M종)을 그 진행(코인 N', 도감 M'종)으로 바꿀까요? 지금 진행은 지금 코드로 서버에 남아 있어요." → 예: 내 코드를 그 코드로 바꾸고 서버본 적용. 바꾸기 전에 지금 진행을 지금 코드로 올려 둔다(dirty 이면).
4. 같이 하기 방 안에서는 이 메뉴를 막는다 (생김새가 바뀌어 방과 어긋나지 않게). 방을 나온 뒤에 한다.

## 허브 로그인 전환 (⚠️ 나중에 반드시 할 일)

**복구 코드는 허브 로그인이 생기기 전까지 쓰는 임시 식별 방식이다. 허브 로그인이 구현되면 로그인 방식으로 바꿔야 한다.**

- 바꾸는 방법(예정): 허브가 게임을 열 때 서명된 토큰(`hub_token`, JWT: `sub` = 허브 유저 ID, `aud` = `rinfish`, 몇 분 만료)을 붙인다. 워커는 허브 공개키(JWKS)로 서명을 검증한다.
- 저장 객체 이름을 `sha256(복구 코드)` 대신 허브 유저 ID 로 정한다. 이미 복구 코드로 쌓인 진행은 **"이 코드의 진행을 내 허브 계정으로 옮기기"** 를 한 번 해서 넘긴다 (코드 입력 → 서버가 그 저장본을 허브 계정 객체로 복사).
- 전환 뒤 복구 코드 화면은 "허브로 로그인" 으로 바꾸고, 코드 입력은 옮기기용으로만 남긴다.
- 그래서 1단계 코드는 식별을 한곳(`cloudSave` 의 인증 머리말 만들기, 워커의 "요청 → 객체 이름" 함수 하나)에만 두어 갈아끼우기 쉽게 한다.
- 허브 개발자와 논의할 것: 허브 유저 고유 ID, `hub_token` 형식·서명 방식(RS256/ES256 + JWKS), 허브를 안 거친 사람의 "허브로 로그인 후 돌아오기" 흐름, game-entry-contract v4.

## 2단계(조작 막기)를 위한 여지

- 1단계 서버는 `data` 를 그대로 보관만 한다. 2단계에서는 같은 `Save` 객체가 판매·구매·구역 열기·사냥 보상을 직접 계산하게 바꾼다 (같이 하기 우선).
- 그래서 저장본을 서버에서 한 객체가 순서대로 다루는 지금 구조(Durable Object)를 그대로 쓸 수 있다.

## 하지 않는 것 (1단계)

- 서버에서 저장 내용 검증·치트 방지
- 마지막 위치·설정 서버 저장
- 랭킹·통계 (필요하면 D1 추가)
- 오래된 저장 정리
- 탭 두 개 동시 실행 막기 (충돌 규칙으로 처리)

## 오류 처리 요약

| 상황 | 동작 |
|---|---|
| 서버 응답 없음·5xx | 사본으로 계속, `pending`, 다시 시도 (5→15→30초) |
| `409` | 서버본 적용 + 토스트 |
| `401` (코드 형식 틀림) | 저장된 코드가 깨진 것: 새 코드를 만들고 지금 사본을 올린다 |
| `413` | 올리지 않고 콘솔 경고 (생기면 안 되는 일) |
| localStorage 못 씀(시크릿 일부) | 기존처럼 저장 없이 플레이. 코드도 유지되지 않음 |
| 서버본이 깨진 JSON | 기존 `merge` 가 기본값으로 채운다 |

## 테스트

**단위 (vitest)**

- 복구 코드: 생성 길이·글자, 입력 정리(소문자·`-`·공백), 틀린 형식 거절.
- 저장 주소 만들기: `wss→https`, `ws→http`, 끝 `/` 처리.
- 서버 규칙(`server/src/saveRules.ts`, 순수 함수): `baseRev` 일치 → 저장·`rev+1`, 불일치 → 409 와 최신본, 첫 저장 `baseRev 0`, 크기 한도, JSON 아님.
- `cloudSave` 동기화 판단(순수 함수): 시작할 때 404/최신/같음/실패 → 할 일, 409 → 적용, 재시도 간격.
- `dirty` 표시: persist 저장 → dirty, 성공 → 깨끗.

**통합 (기존 tools 방식)**

- `tools/save-smoke.mjs`: 로컬 `wrangler dev` 서버에 대해 GET 404 → PUT → GET → 낡은 baseRev PUT 409 → CORS 머리말 확인.
- 헤드리스 브라우저: 새 브라우저에서 진행 만들기 → 저장 대기 → localStorage 지우기 → 코드로 이어 하기 → 코인·도감 복원 확인. 탭 두 개 충돌 시 토스트.
- 기존 검사 그대로 통과: vitest, tsc, lint, build, meadow-check, room-smoke, multiplayer, hub-entry.

# 진행 서버 저장 설계 (1단계: 진행 안 날아가게)

> 지금 섬마을의 진행(`progressStore`, 키 `fishing-island-save-v1`)은 브라우저 localStorage 에만 있다. 브라우저 데이터를 지우거나 주소가 바뀌면(rinfish → seommaeul 때처럼) 진행이 사라진다. 이 설계는 진행을 Cloudflare 서버(Durable Object 저장소)에 보관한다. 사용자 결정(2026-11-26)을 따른다.
>
> 리뷰 반영: 최종 검토·Codex 리뷰(2026-11-26). 덮어쓰기 전 백업과 되돌리기, 탭 하나만, 쓰기 요청 ID, 제한 시간, 남용 막기, 객체 이름 접두어를 더했다.

## 먼저 읽기: 이 문서에 나오는 말

| 말 | 뜻 |
|---|---|
| **정본 / 사본** | 정본은 서버에 있는 진짜 저장, 사본은 브라우저(localStorage)에 있는 복사본. 게임은 사본으로 바로 돌고, 사본을 정본에 올린다 |
| **복구 코드** | 내 진행을 찾는 열쇠 (`QX7K-29PM-…`). 비밀번호와 같다 |
| **저장 번호** (코드 이름 `rev`) | 서버에 저장될 때마다 1씩 오르는 번호. 어느 쪽이 더 최신인지 가리는 데 쓴다 |
| **맞춘 번호** (`syncedRev`) | 이 브라우저가 서버와 마지막으로 같았던 때의 저장 번호 |
| **안 올린 변경** (`dirty`) | 사본이 바뀌었는데 아직 서버에 안 올린 상태. 올리면 없어진다 |
| **Save 객체** | 복구 코드 하나마다 서버에 하나씩 있는 Durable Object. 그 사람 진행을 보관하고, 요청을 하나씩 차례로 처리한다 |
| **해시** | 글자를 되돌릴 수 없게 섞은 지문. 서버는 복구 코드 원문 대신 해시만 쓴다 |
| **쓰기 요청 ID** (`writeId`) | 올릴 때마다 붙이는 무작위 이름표. 서버가 저장과 함께 기억해 두어, 응답을 못 받은 브라우저가 "그 저장이 내 것인지" 알아본다 |
| **결과를 모르는 쓰기** (`pending`) | 보냈지만 성공 응답을 아직 못 받은 쓰기 (쓰기 요청 ID 와 그때 맞춘 번호). 보내기 **전에** 브라우저에 적어 둔다 |
| **백업** | 서버 것으로 덮어쓰기 직전의 이 브라우저 진행 사본 한 벌. 메뉴에서 되돌릴 수 있다 |
| **게임 잠금** | 한 브라우저에서 게임 탭이 하나만 돌게 하는 브라우저 잠금(Web Locks `seommaeul-game`) |

## 목표와 성공 기준

- 진행이 서버에 저장되어, 브라우저 데이터를 지우거나 다른 기기·주소에서 들어와도 **복구 코드**로 되찾을 수 있다.
- 서버나 인터넷이 끊겨도 혼자 하기는 지금처럼 플레이된다. 돌아오면 밀린 저장을 올린다.
- 같은 진행을 두 곳(기기 두 대, 브라우저 두 개)에서 동시에 해도 저장이 뒤섞이지 않는다. 늦은 쪽이 최신을 받아 이어 하고, 덮어쓰인 쪽 진행은 백업으로 되돌릴 수 있다. 같은 브라우저의 탭은 하나만 돈다.
- 기존 유저의 진행은 첫 접속 때 자동으로 서버로 올라간다. 아무것도 잃지 않는다.
- 서버 주소(`VITE_ROOM_SERVER`)가 없는 개발 환경에서는 지금과 똑같이 브라우저에만 저장한다.

## 정해진 규칙 (사용자 결정)

| 주제 | 결정 |
|---|---|
| 단계 | **1단계: 진행 안 날아가게**(이 문서). **2단계: 조작(치트) 막기**는 나중에 별도 설계 |
| 서버 장애 | **계속 플레이**. 브라우저 사본으로 진행하고, 서버가 돌아오면 올린다 |
| 식별 | 우선 **복구 코드**. **허브 로그인이 구현되면 로그인 방식으로 바꾼다** (아래 "허브 로그인 전환" 참고) |
| 저장 방식 | 방 서버 워커(`rinfish-rooms`)에 저장 주소를 더하고, **복구 코드마다 Save 객체 하나** |
| 충돌 | 저장 번호로 판정. **서버가 더 최신이면 서버 것을 받는다**. 단, 받으면 안 올린 진행이 사라질 때는 **먼저 이 브라우저 사본을 백업**하고, ESC 메뉴에서 되돌릴 수 있게 한다 (리뷰 뒤 결정) |
| 탭 | **한 브라우저에서 게임 탭은 하나만**. 두 번째 탭은 게임 대신 안내를 보인다 (리뷰 뒤 결정) |
| 코드 재발급 | 코드 재발급·이전 코드 끄기는 지금 하지 않는다. 허브 로그인 전환 때 함께 한다 |

## 무엇을 어디에 두나

| 위치 | 데이터 |
|---|---|
| **서버 (Save 객체)** | `progressStore` 저장본 전체: 생김새(look), 코인, 장비, 탄약, 물고기·재료·간식·미끼·사료, 도감, 사격장 최고 점수, 플레이 시간, 연 구역, 은지 집 문, 어항, 가게 오늘 수량, 체력·배고픔, 혼자 시계 (저장본 버전 번호 포함) |
| **브라우저만** | 설정(`fishing-island-settings-v1`), 마지막 위치(`fishing-island-place-v1`), 닉네임·마지막 방(`fishing-island-net-v1`), 허브 복귀 주소(sessionStorage), 애셋 캐시 |
| **브라우저 (새로)** | 복구 코드, 맞춘 번호, 안 올린 변경, 결과를 모르는 쓰기 (`seommaeul-cloud-v1`). 덮어쓰기 전 백업 (`seommaeul-cloud-backup-v1`) |
| **브라우저 (그대로, 역할만 바뀜)** | `fishing-island-save-v1` 는 이제 **사본**. 정본은 서버 |

마지막 위치는 이번에 옮기지 않는다. 다른 기기에서는 선착장에서 시작할 뿐이라 손해가 작다.

## 구조

```
브라우저                                     Cloudflare 워커 rinfish-rooms
┌───────────────────────────┐               ┌──────────────────────────────────┐
│ progressStore (게임 진행)   │               │ /rooms/<id>  → Room  (그대로)      │
│  └ localStorage 사본        │               │ /save        → Save 객체          │
│ cloudSave (서버와 주고받기)  │──HTTPS(JSON)──▶│    이름 = 복구 코드의 해시          │
│  └ 복구 코드·맞춘 번호       │               │    보관: 저장 번호, 진행, 저장 시각  │
└───────────────────────────┘               └──────────────────────────────────┘
```

### 서버

- `server/wrangler.toml` 에 Save 객체를 등록한다 (바인딩 `SAVE`, 클래스 `Save`, 마이그레이션 `v2`).
- 저장 주소는 방 서버 주소에서 만든다: `wss://…` → `https://…`, `ws://…` → `http://…`, 뒤에 `/save`.
- 복구 코드는 **요청 머리말**(`Authorization: Bearer <코드>`)로 받는다. 주소(URL)에 넣지 않는다. 주소는 접속 기록에 남기 때문이다.
- 워커는 코드 모양을 검사한 뒤, `code:` + 코드의 해시(sha256)를 이름으로 Save 객체를 찾아 넘긴다. **코드 원문은 어디에도 저장하지 않는다.** `code:` 접두어는 나중에 허브 유저(`hub:`)와 이름이 겹치지 않게 하려는 것이다 (첫 배포 전에 정함).
- Save 객체는 `save` 칸 하나에 `{ 저장 번호(rev), 진행(data), 저장 시각(savedAt), 쓰기 요청 ID(writeId) }` 를 보관한다.

| 요청 | 동작 | 응답 |
|---|---|---|
| **읽기** `GET /save` | 저장본을 돌려준다 | 있으면 `200` + 저장 번호·진행·시각·쓰기 요청 ID / 없으면 `404` |
| **쓰기** `PUT /save` (보내는 것: 내가 맞춘 번호 `baseRev`, 진행 `data`, 쓰기 요청 ID `writeId`) | 내가 맞춘 번호가 서버 저장 번호와 같으면(처음이면 둘 다 0) 저장하고 번호를 1 올린다. 쓰기 요청 ID 도 같이 기억한다 | `200` + 새 저장 번호 |
| | 다르면 = 그사이 다른 곳에서 저장했다 (또는 응답을 못 받은 내 앞 쓰기가 이미 들어갔다) → 저장하지 않는다 | `409` + 서버 최신본(쓰기 요청 ID 포함) |
| 잘못된 요청 | 코드 모양이 틀림 `401`, 너무 큼 `413`, 진행이 JSON 객체가 아니거나 쓰기 요청 ID 가 글자가 아니거나 64자보다 김 `400`, 호출이 너무 많음 `429`, 없는 주소 `404` | |

- 진행 크기 한도 **256KB**. 지금 저장본은 몇 KB 라 넉넉하다.
- 1단계 서버는 진행 내용을 검사하지 않고 보관만 한다. 불러올 때 게임이 기존 검사(버전 올리기 `migrate`, 값 검증 `merge`)를 그대로 거친다.
- 다른 주소에서 오는 요청 허용(CORS): 게임 주소(`https://seommaeul.vercel.app`, 로컬 개발 `http://localhost:*`, `http://127.0.0.1:*`)만 허용한다. 허용 목록은 워커 안에 상수로 둔다.
- 오래 안 쓴 저장은 1단계에서 지우지 않는다.

#### 남용 막기

CORS 는 브라우저만 막을 뿐 직접 호출(curl 등)은 막지 못한다. 그래서 워커 앞단에서 따로 막는다.

- **크기 먼저 검사**: 워커가 `Content-Length` 를 보고 256KB 를 넘으면 본문을 읽기 전에 `413`. 길이를 안 밝히거나 속여도 Save 객체가 본문을 한도+1 바이트까지만 읽고 멈춰 `413`.
- **호출 수 제한**: Cloudflare 호출 수 제한(`[[ratelimits]]` 바인딩 `SAVE_LIMIT`)으로 **IP(`CF-Connecting-IP`)마다 1분에 60번**. 넘으면 `429`(CORS 머리말 포함). 게임은 보통 몇 초~15초에 한 번 올리므로 넉넉하다.
- 브라우저는 `429` 를 서버 오류처럼 다룬다 (대기 중, 5→15→30초 다시 시도).

### 복구 코드

- 쓰는 글자: `23456789ABCDEFGHJKMNPQRSTVWXYZ` (헷갈리는 0·O·1·I·L·U 를 뺀 30자). **20자**라서 맞힐 확률이 사실상 0이다(약 98비트). 보여 줄 때는 `QX7K-29PM-H4TB-8WNC-5RDA` 처럼 4자씩 끊는다.
- 브라우저의 안전한 난수(`crypto.getRandomValues`)로 만든다. 입력받을 때는 대문자로 바꾸고 `-`·공백을 지운 뒤 글자·길이를 검사한다. 서버도 같은 검사를 한다.
- 코드는 비밀번호와 같다. 아는 사람은 그 진행을 읽고 덮어쓸 수 있다. 화면에 "남에게 보여 주지 마세요" 를 적는다.

### 브라우저 쪽 (`cloudSave`)

게임 진행 저장소(`progressStore`)가 브라우저에 쓰는 길목을 감싸서, 서버와 주고받는 모듈 하나를 둔다. 게임 로직은 바뀌지 않는다.

기억하는 것:
- 복구 코드
- 맞춘 번호 (서버와 마지막으로 같았던 저장 번호)
- 안 올린 변경이 있는지
- 결과를 모르는 쓰기 (`pending` = 쓰기 요청 ID 와 그때 맞춘 번호)
- 지금 상태: 서버 없음 / 올리는 중 / 저장됨 / 대기 중 (화면 구석 표시용)

앞의 넷은 브라우저 `seommaeul-cloud-v1` = `{ code, syncedRev, dirty, pending }` 에 둔다. 덮어쓰기 전 백업은 `seommaeul-cloud-backup-v1` = `{ code, savedAt, raw }` (한 칸, 새것이 이긴다).

#### 시작할 때 (로딩 화면 동안)

1. 이 탭이 게임 잠금을 잡는다 (아래 "탭 하나만"). 못 잡으면 여기서 멈춘다.
2. 브라우저 사본으로 게임 상태를 채운다 (지금과 같음).
3. 복구 코드가 없으면 새로 만든다.
4. 서버에서 내 저장을 읽는다 (최대 8초, 아래 "제한 시간").
   - **서버의 최신이 내 결과를 모르는 쓰기** (쓰기 요청 ID 가 같고 번호가 더 큼) → 응답만 잃은 내 저장이다. 받지 않고 그 번호를 맞춘 번호로 삼은 뒤 지금 사본을 올린다.
   - **서버에 없음** → 지금 사본을 올린다. **기존 유저의 진행이 이때 서버로 옮겨진다.** 새 유저는 처음 상태가 올라간다. 올리기 전에 "안 올린 변경 있음" 으로 적어 두어, 첫 올리기가 실패해도 다시 시도한다.
   - **서버 번호가 내 맞춘 번호보다 큼** (다른 기기에서 더 했음) → 서버 것을 받는다 (아래 "서버 것 받기"). 이전에 남은 안 올린 변경이 있었거나 **읽는 사이 플레이해서 사본이 바뀌었으면**, 받기 전에 백업하고 "다른 곳에서 한 진행으로 바꿨어요. 이전 진행은 메뉴에서 되돌릴 수 있어요" 안내를 띄운다.
   - **서버 번호와 내 맞춘 번호가 같음** → 안 올린 변경이 있으면 올리고, 없으면 그대로.
   - **응답 없음·시간 초과·응답 모양이 틀림** → 사본으로 플레이하고 "대기 중". 30초마다 다시 시도한다.
5. 로딩 화면은 이 단계를 3초까지만 기다린다. 보통은 모델을 받는 동안 끝난다. 읽기는 3초 뒤에도 계속되며, 늦게 와도 위 규칙(백업 포함)을 그대로 따른다.

#### 플레이 중

- 게임이 사본에 저장할 때마다 "안 올린 변경 있음" 으로 표시한다. 탄 한 발처럼 잦은 저장은 지금처럼 모아서 쓴다(`deferrableStorage`).
- 안 올린 변경이 있으면 **마지막 변경 뒤 3초 동안 더 안 바뀔 때** 서버에 올린다. 계속 바뀌는 중이라도 **15초에 한 번은** 올린다. 물고기를 연달아 잡거나 총을 연사할 때 매번 보내지 않고 묶어 보내기 위해서다.
- 올릴 때는 "내가 맞춘 번호는 몇 번" 과 **쓰기 요청 ID** 를 같이 보낸다. 보내기 전에 그 ID 를 "결과를 모르는 쓰기" 로 브라우저에 적어 둔다. 성공하면 서버가 준 새 번호를 맞춘 번호로 기억하고 "안 올린 변경 없음", 결과를 모르는 쓰기도 지운다. 올리는 사이 또 바뀌었으면 성공해도 "대기 중" 으로 두고 다시 올린다.
- 실패(못 닿음·시간 초과·5xx·429)하면 결과를 모르는 쓰기를 남겨 두고, 다시 보낼 때 **같은 ID** 를 쓴다. 앞 쓰기가 사실 들어갔다면 서버가 409 와 그 ID 를 돌려주므로, 브라우저는 "내 것" 으로 알아보고 받지 않는다: 그 번호에 맞춘 뒤 지금 사본을 다시 올린다. 그래서 응답을 잃어도 자기 변경을 충돌로 착각해 지우지 않는다.

예:
```
0초  물고기 잡음 → 안 올린 변경 있음
1초  또 잡음 → 3초 다시 셈
4초  3초간 조용함 → 올림 ("나는 7번까지 맞췄어")
     서버도 7번 → 저장하고 8번 → 맞춘 번호 = 8, 안 올린 변경 없음
```

- 탭을 숨기거나 닫을 때: 모아 둔 저장을 먼저 사본에 쓰고, 바로 서버에 올린다. 페이지가 닫혀도 끝까지 보내지는 방식(`fetch` 의 `keepalive`)을 쓴다.
- 올리기에 실패하면 "대기 중" 으로 두고 5초 → 15초 → 30초 간격으로 다시 시도한다. 사본은 이미 브라우저에 있으니 진행은 잃지 않는다.
- 서버 응답은 쓰기 전에 모양을 검사한다: 읽기·409 본문은 정수 번호(1 이상)와 객체 진행(쓰기 요청 ID 는 있으면 글자), 성공 본문은 정수 번호. 틀리면 실패로 보고 받지 않는다.

#### 제한 시간

- 모든 요청은 시간 제한을 둔다 (`AbortController`): **읽기 8초, 쓰기 10초**. 넘으면 끊고 실패로 본다.
- 시작 읽기가 시간 초과면 "응답 없음" 과 같다 (30초 뒤 다시). 로딩 화면은 원래대로 3초까지만 기다린다.
- 쓰기가 시간 초과면 서버가 저장했는지 모른다. 결과를 모르는 쓰기로 남겨 같은 쓰기 요청 ID 로 다시 보내므로 안전하다.

#### 충돌 (서버가 "그사이 다른 곳에서 저장했어" 하고 거절)

- 다른 기기가 먼저 저장했다는 뜻이다 (409 본문의 쓰기 요청 ID 가 내 결과를 모르는 쓰기와 같으면 충돌이 아니다: 위 "플레이 중").
- 서버 것을 받는다. 받기 **전에** 이 브라우저 사본을 백업한다 (사본이 서버 것과 똑같으면 백업하지 않는다).
- 안내: 백업했으면 "다른 곳에서 한 진행으로 바꿨어요. 이전 진행은 메뉴에서 되돌릴 수 있어요", 아니면 "다른 곳에서 한 진행으로 바꿨어요".
- 오프라인에서 오래 한 기기라도 진행이 사라지지 않는다: 백업에 남아 있고, 사용자가 메뉴에서 되돌릴 수 있다.

예:
```
기기 A: 7번까지 맞춤 → 올림 → 서버 8번
기기 B: 아직 7번까지 맞춘 줄 앎 → 올림 → 서버 "나는 8번이야" 거절 + 8번 내용
기기 B: 지금 사본을 백업 → 8번 내용으로 바꾸고 안내 → 이어서 플레이
기기 B: (원하면) 메뉴에서 "덮어쓰기 전 진행으로 되돌리기" → 백업이 9번으로 올라감
```

#### 덮어쓰기 전 진행으로 되돌리기

- 백업은 한 칸이다 (`seommaeul-cloud-backup-v1` = `{ code, savedAt, raw }`). 새로 백업하면 앞 백업을 덮는다.
- 백업에는 **만들 때의 복구 코드**를 같이 적는다. 지금 코드와 같을 때만 보이고 되돌릴 수 있다. 다른 코드의 백업을 되돌리면 그 코드의 진행을 덮어 버리기 때문이다. 코드를 바꾼 뒤 원래 코드로 돌아오면 다시 보인다. 코드가 적혀 있지 않은 백업은 없는 것으로 본다.
- 백업이 있으면 ESC 메뉴 「☁️ 진행 저장」에 "덮어쓰기 전 진행으로 되돌리기 (코인 N, 도감 M종, <시각>)" 와 작은 「백업 지우기」가 보인다. 같이 하기 방 안에서는 숨긴다 (생김새가 방과 어긋나므로).
- 누르면 확인 → 사본을 백업 원문으로 바꾸고 게임 상태를 다시 읽은 뒤, "안 올린 변경 있음" 으로 표시해 **가장 새 진행으로**(서버 번호 + 1) 올린다. 백업은 지우고 "덮어쓰기 전 진행으로 되돌렸어요" 안내.

#### 서버 것 받기

- 서버 진행을 브라우저 사본에 쓰고, 게임 진행 저장소가 사본을 다시 읽게 한다 (`persist.rehydrate()`). 기존 검사(버전 올리기, 값 검증)를 그대로 거친다.
- 맞춘 번호를 서버 번호로 바꾸고 "안 올린 변경 없음" 으로 둔다.
- 낚시나 요리 도중에 바뀌면 화면과 어긋날 수 있다. 시작할 때는 로딩 화면 뒤라 괜찮고, 플레이 중 충돌은 드물어서 1단계에서는 그대로 바꾼다.

#### 탭 하나만

- 같은 브라우저의 탭들은 진행 사본과 `seommaeul-cloud-v1` 을 나눠 쓰지만 기억(맞춘 번호, 타이머)은 따로라, 둘이 동시에 돌면 서로의 사본·저장 정보를 덮어쓸 수 있다. 그래서 탭을 하나로 막는다.
- 페이지가 열리면 `navigator.locks.request('seommaeul-game', { ifAvailable: true })` 로 게임 잠금을 바로 잡을 수 있는지 본다. 잡으면 페이지가 닫힐 때까지 쥐고, 그다음에 게임을 그리고 서버 맞추기를 시작한다.
- 못 잡으면 (새로고침 직후 옛 페이지가 아직 놓지 않았을 수 있어) 0.5초 뒤 한 번 더 본다. 그래도 막히면 게임을 그리지 않고 "다른 탭에서 섬마을을 하고 있어요. 그 탭을 닫고 새로고침해 주세요." 만 보인다. 서버 맞추기도 하지 않는다.
- `navigator.locks` 가 없거나 막힌 브라우저는 잠금 없이 간다 (예전처럼).
- 다른 기기·다른 브라우저끼리는 위 충돌 규칙(백업 포함)으로 처리한다.

#### 서버 주소가 없을 때

- 아무것도 하지 않는다. 복구 코드 화면도 숨긴다. 지금과 똑같다.

## 화면

| 곳 | 내용 |
|---|---|
| 화면 구석 | `☁️ 저장됨` / `☁️ 저장 중…` / `☁️ 저장 대기 중` (작게). 서버 주소가 없으면 없음 |
| ESC 메뉴 → 「☁️ 진행 저장」 | 내 복구 코드(4자씩), 「복사」 버튼(못 하면 "복사하지 못했어요. 코드를 직접 적어 두세요"), 안내: "브라우저를 지우거나 다른 기기에서 이어 하려면 이 코드가 필요해요. 남에게 보여 주지 마세요." |
| 같은 창 (백업이 있을 때, 방 밖에서만) | "덮어쓰기 전 진행으로 되돌리기 (코인 N, 도감 M종, <시각>)" → 확인 → 되돌리기. 작은 「백업 지우기」 |
| 두 번째 탭 | 게임 대신 "다른 탭에서 섬마을을 하고 있어요. 그 탭을 닫고 새로고침해 주세요." |
| 같은 창 | 「코드로 이어 하기」 입력칸 (아래) |
| 시작 창 | 「🔑 코드로 이어 하기」 버튼 → 같은 입력칸 |

**코드로 이어 하기**

1. 코드를 입력하면 모양을 검사하고, 그 코드로 서버 저장을 읽는다.
2. 없으면 → "그 코드로 저장된 진행이 없어요".
3. 있으면 → 확인 창: "지금 이 브라우저의 진행(코인 N, 도감 M종)을 그 진행(코인 N', 도감 M'종)으로 바꿀까요? 지금 진행은 지금 코드로 서버에 남아 있어요." → 예: 지금 진행을 먼저 지금 코드로 다 올려 두고(올리다 409 면 서버 것을 받고 백업한 뒤 이어 간다), **그 코드의 저장을 지금 다시 읽어**(미리보기 뒤 바뀌었을 수 있다) 내 코드를 새 코드로 바꾸고 받는다.
   - 시작 맞추기가 아직 안 끝났거나, 지금 진행을 올리지 못했거나, 그 저장을 다시 읽지 못했으면(없어짐 포함) 아무것도 바꾸지 않고 "지금은 바꾸지 못했어요. 서버 연결을 확인하고 잠시 뒤 다시 해 주세요".
4. 같이 하기 방 안에서는 이 메뉴를 막는다. 생김새가 바뀌면 방과 어긋나기 때문이다. 방을 나온 뒤에 한다.

## 허브 로그인 전환 (⚠️ 나중에 반드시 할 일)

**복구 코드는 허브 로그인이 생기기 전까지 쓰는 임시 방식이다. 허브 로그인이 구현되면 로그인 방식으로 바꿔야 한다.**

- 바꾸는 방법(예정): 허브가 게임을 열 때 위조할 수 없는 입장권(`hub_token`, 서명된 JWT)을 붙여 준다. 안에는 허브 유저 ID(`sub`), 어느 게임용인지(`aud` = `rinfish`), 몇 분 뒤 만료가 들어 있다. 워커는 허브가 공개한 공개키(JWKS)로 진짜인지 확인한다.
- Save 객체 이름을 `code:` + 복구 코드의 해시 대신 `hub:` + 허브 유저 ID 로 정한다 (접두어가 달라 둘이 겹칠 일이 없다). 이미 복구 코드로 쌓인 진행은 **"이 코드의 진행을 내 허브 계정으로 옮기기"** 를 한 번 해서 넘긴다 (코드 입력 → 서버가 그 저장을 허브 계정 쪽으로 복사).
- 전환 뒤 복구 코드 화면은 "허브로 로그인" 으로 바꾸고, 코드 입력은 옮기기용으로만 남긴다.
- 그래서 1단계 코드는 "누구인지 알아보는 부분" 을 한곳에만 둔다: 브라우저는 요청 머리말 만드는 함수 하나(`authHeader`), 워커는 "요청 → Save 객체 이름" 함수 하나(`saveObjectName`, `server/src/saveRules.ts`). 이 둘만 갈아끼우면 된다.
- 코드 재발급·이전 코드 끄기는 허브 로그인 전환 때 함께 한다 (Codex 리뷰 2026-11-26). 옮기기는 코드 소유를 확인한 뒤 계정 쪽에 조건부로 한 번만 연결하는 방식으로, 그때 따로 설계한다.
- 허브 개발자와 논의할 것: 허브 유저 고유 ID, 입장권 형식·서명 방식(RS256/ES256 + JWKS), 허브를 안 거친 사람의 "허브로 로그인하고 돌아오기" 흐름, game-entry-contract v4.

## 2단계(조작 막기)를 위한 여지

- 1단계 서버는 진행을 그대로 보관만 한다. 2단계에서는 같은 Save 객체가 판매·구매·구역 열기·사냥 보상을 직접 계산하게 바꾼다 (같이 하기 먼저).
- Save 객체는 한 사람의 요청을 하나씩 차례로 처리하므로, 2단계에서도 이 구조를 그대로 쓸 수 있다.

## 하지 않는 것 (1단계)

- 서버에서 진행 내용 검사·치트 막기
- 마지막 위치·설정 서버 저장
- 랭킹·통계 (필요하면 D1 추가)
- 오래된 저장 정리
- 코드 재발급·이전 코드 끄기는 허브 로그인 전환 때 함께 한다 (Codex 리뷰 2026-11-26)
- 두 진행을 나란히 보여 주고 고르게 하기 (자동으로 서버 것을 받고, 백업과 되돌리기로 대신한다)

## 문제가 생겼을 때

| 상황 | 동작 |
|---|---|
| 서버 응답 없음·서버 오류(5xx) | 사본으로 계속, "대기 중", 다시 시도 (5→15→30초) |
| 시간 초과 (읽기 8초, 쓰기 10초) | 실패와 같다. 쓰기는 결과를 모르는 쓰기로 남겨 같은 쓰기 요청 ID 로 다시 보낸다 |
| 호출이 너무 많음(429) | 서버 오류와 같다: "대기 중", 다시 시도 |
| 그사이 다른 곳에서 저장함(409) | 지금 사본 백업 → 서버 것 받기 + 안내 (메뉴에서 되돌리기) |
| 409 인데 내 앞 쓰기였음 (쓰기 요청 ID 같음) | 받지 않는다. 그 번호에 맞추고 지금 사본을 다시 올린다 |
| 서버 응답 모양이 틀림 | 받지 않고 실패로 본다 |
| 코드 모양 틀림(401) | 저장된 코드가 깨진 것: 새 코드를 만들고 지금 사본을 올린다 |
| 너무 큼(413) | 다시 시도하지 않고 "대기 중". "진행이 너무 커서 서버에 저장하지 못했어요" 를 (탭마다) 한 번 안내 |
| 백업을 되돌리고 싶음 | ESC 메뉴 「☁️ 진행 저장」 → 되돌리기 (방 밖에서). 필요 없으면 「백업 지우기」 |
| 같은 브라우저에 탭을 또 엶 | 두 번째 탭은 게임 대신 안내 |
| 브라우저 저장소를 못 씀(일부 시크릿 창) | 지금처럼 저장 없이 플레이. 코드도 유지되지 않음 |
| 서버 진행이 깨짐 | 기존 값 검증(`merge`)이 기본값으로 채운다 |

## 테스트

**단위 (vitest)**

- 복구 코드: 만든 코드의 길이·글자, 입력 정리(소문자·`-`·공백), 틀린 모양 거절.
- 저장 주소 만들기: `wss→https`, `ws→http`, 끝 `/` 처리.
- 서버 규칙(`server/src/saveRules.ts`, 순수 함수): 맞춘 번호 일치 → 저장·번호 +1, 불일치 → 거절과 최신본, 첫 저장(0), 크기 한도, JSON 아님.
- 브라우저 동기화 판단(순수 함수): 시작할 때 없음/서버가 최신/같음/실패 → 할 일, 거절 → 서버 것 받기, 다시 시도 간격.
- 안 올린 변경 표시: 사본 저장 → 있음, 올리기 성공 → 없음.
- 리뷰 반영: 응답을 잃은 쓰기의 재시도(409·시작 읽기에서 내 것으로 알아봄), 무응답 읽기·쓰기 시간 초과, 늦게 온 시작 읽기의 백업, 백업 되돌리기·지우기, 코드 바꾸기(시작 전 거절·다시 읽기·409), 응답 모양 검사, 413 안내 한 번, 게임 잠금(잡힘·막힘·다시 보기·없음), 크기 먼저 검사·본문 한도 읽기, 객체 이름 접두어.

**통합 (기존 tools 방식)**

- `tools/save-smoke.mjs`: 로컬 서버(`wrangler dev`)에 대해 읽기 404 → 쓰기 → 읽기 → 낡은 번호로 쓰기 409 → CORS 머리말 → 쓰기 요청 ID(409 에 돌아옴, 너무 길면 400) → 큰 본문 413 → 호출 수 제한 429 확인.
- 헤드리스 브라우저(`tools/cloud-check.mjs`): 새 브라우저에서 진행 만들기 → 같은 프로필 두 번째 탭 막힘 → 저장 대기 → 새 브라우저에서 코드로 이어 하기 → 코인 복원 확인. 두 곳 충돌 때 안내와 백업.
- 기존 검사 그대로 통과: vitest, tsc, lint, build, meadow-check, room-smoke, multiplayer, hub-entry.
